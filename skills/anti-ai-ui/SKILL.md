# Anti-AI UI

让界面像为真实任务设计的产品：层级清楚、内容具体、操作可信、视觉有自己的依据。“AI 味”在这里是对模板化症状的简称，不是生成来源检测，也不是统一改成黑白极简。

## 先确定任务

- **新建界面**：先确定使用者、主要任务、需要比较的信息和已有品牌，再选择结构与视觉方向。
- **改造界面**：检查目标页面及关联组件、文案和状态；保持已授权范围内的业务行为，优先解决用户点名的问题。
- **只做审查**：提供有位置、有影响、有改法的发现；用户没要求改代码时不要顺手重构。

从现有代码、截图和需求能判断的内容自行判断。只有会改变关键流程的缺失信息才询问；把工程假设留在工作沟通中，不追加到产品页面当说明文字。只有截图时，区分可见问题与尚未验证的交互。

## 核心约束

1. **先定信息优先级，再修饰容器。** 明确“用户现在要做什么、凭什么决定、下一步在哪”。后台可以密集，营销页可以有表现力；不要套用同一首屏和卡片网格。
2. **装饰必须有依据。** 默认不为普通卡片添加彩色单侧描边、发光阴影或装饰徽章。保留有明确意义的选中态、告警、引用或品牌处理；状态不能只靠颜色。不要全局删除 `border-left`，它也可能是分隔线或必要状态。
3. **按内容关系选结构。** 比较记录用表格，连续条目用列表，同一对象的属性用分组，独立内容单元可以用卡片。优先以对齐、间距和标题建立层级，避免为每段文字再套一层容器。
4. **首层只放当前任务需要的内容。** 高频操作、关键比较字段、状态、输入约束和会影响决定的风险留在可见位置；罕用细节有明确入口。不能把信息爆炸简单改成“所有东西都折叠”。
5. **每句话都要提供新增信息。** 删除标题复述、按钮教学、无依据的宣传和泛化兜底。动作写清对象，状态写清事实；不要为了“去 AI 味”把真实的不确定性改成肯定语气。
6. **保留产品的辨识度与可用性。** 优先沿用现有组件、设计 token 和品牌。颜色、字体、渐变、圆角本身不是错误；不强换技术栈，不为独特而牺牲可读性、点击目标、标签和键盘操作。

## 执行方式

### 1. 画出当前任务的内容层级

用简短工作笔记分清：主要对象与操作、决定所需信息、低频详情、无用重复。这份笔记是设计依据，不是要渲染到页面的新模块。

按照用户任务选择第一屏内容。不要硬凑 KPI 数量、卡片列数、固定的说明字数或“一个页面只能一个按钮”。一个操作区域应有清晰的主次；专家工作台可有多个高频动作。

### 2. 找到症状并判断是否成立

遇到视觉模板、卡片和信息密度问题，按需查阅 [反模式与替代方案](references/anti-patterns.md)。遇到重复说明、泛化提示、错误或数据不确定性，查阅 [文案与信息分层](references/content-and-disclosure.md)。需要具体改造尺度时查阅 [原创前后案例](references/examples.md)。

每个候选问题都要回答：在哪个组件或区域？它妨碍哪个任务？用户因此多读、误解或多点了什么？是否存在合理例外？没有实际影响的纯审美差异，不升级成缺陷。

源码搜索可帮助定位 `border-l-*`、`border-left`、渐变、重复 Card，以及“温馨提示”“可能”“仅供参考”等词，但只作为检查线索。不要基于关键字自动修复或声称能够量化“AI 含量”。

### 3. 按收益顺序修改

先改任务结构和信息位置，再改微文案，最后调整排版、色彩、边界与动效。默认采用影响局部的最小有效改动；若共享组件影响多个页面，先确认影响面。

可以删除重复文字、合并容器、将低频内容移入详情；不要移除业务能力或篡改数据来换取简洁。替代方案必须说明被移走的信息在哪里仍然能找到。

新界面的特色优先来自业务内容、真实图像、排版节奏和交互反馈。不要把“紫色渐变模板”机械换成“奶油底衬线模板”或“黑白线框模板”。

### 4. 用任务验证结果

- 用户能否快速找到主要对象、当前状态、判断依据和下一步？
- 首层留下的信息是否有明确用途？低频详情入口是否具体、可发现？
- 关键错误、权限原因、数据缺口、费用与不可逆影响是否仍在相关位置可见？
- 正常、空、加载、失败、禁用状态是否准确且可操作？未知与数值零是否区分？
- 窄屏、长中文、真实数据量下是否仍能阅读和操作？有无截断关键内容或整页横向溢出？
- 键盘焦点、可见标签、图标按钮名称、对比度及减少动效偏好是否保留？

有可运行界面且有浏览器工具时，实际打开页面检查渲染和受影响的交互（含窄屏），结束后关闭自己启动的服务或标签页。没有运行条件时明确哪些判断来自源码或截图，不声称完成了视觉验收。测试覆盖受影响的行为，不为简单样式修改添加仅复述实现的测试。

## 交付

改造任务交付实际修改，并简述解决了什么、保留了哪些必要信息、如何验证。审查任务只列有证据的问题，按影响排序，允许“没有需要修改的问题”。需要较详细的审查时使用：

| 位置与证据 | 对任务的影响 | 建议修改 | 必须保留的信息或例外 |
|---|---|---|---|

把建议和实施结果分清；不要为证明做过审查而凑问题。无需向产品用户显示此清单或设计过程。
